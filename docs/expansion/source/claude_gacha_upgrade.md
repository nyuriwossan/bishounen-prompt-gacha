## 4. 最優先の非破壊要件

1. 既存の候補ID・保存キー・選択値・ロック状態を無断で削除、改名、上書きしない。必要な移行は明示的な対応表とテストで行う。
2. 旧お気に入り／履歴／保存キャラクター／人物派生／衣装3案／JSONバックアップ／共有URL／戻す・進む／部分再抽選を維持する。
3. ロック値は黙って変更しない。ロック同士が矛盾したら現行どおり抽選を停止し、日本語の理由と解除候補を表示する。
4. 成人男性1名・美形という軸を維持する。**中性的顔×筋肉質、老紳士×黒髪、現代×幻想など、単に意外な組み合わせをhard禁止しない。**
5. 既存の3モード（まとまり重視／バランス／カオス）、おまかせスタイル、辞書除外条件、seedの仕様を保持する。
6. 任意モジュールがOFFならその関連タグを出力しない。禁断・コスプレの条件が新規候補で回避されないこと。特に拘束・目隠し・眼鏡・髪・表情・手の空き・衣装の乱れ・画角との競合を確認する。
7. 文化モチーフから肌色・人種・顔貌を自動決定しない。実在の服飾文化と創作的な「〜風」を区別する。
8. サーバー・外部API・ログインを必須にしない。GitHub Pagesで静的配信し、ローカル保存・オフライン挙動を維持する。
9. 新候補追加で既存の「抽選除外」設定がどうなるか必ず確認する。既存の除外は勝手に解除しない。新候補の許可扱いが変わる場合は、正確な更新通知と利用者が制御できる仕組みを用意する。
10. 新フィールドは旧データを開いた時に自動で顔・髪・衣装を変えてはいけない。旧保存データでは `none`／無効などの互換値を使い、ユーザーが明示的に有効化した後に適用する。
11. 既存版と同一seedの全出力バイト一致は辞書変更後には要求しないが、**同じデータ版・条件・seedなら再現可能**にする。辞書更新で再現性が変わる事実を明記し、DATA_VERSIONを適切に改訂する。
12. 開発前後でブラウザの保存データ消失につながる変更を禁止。バックアップ復元・容量不足・旧形式移行を検証する。

## 5. 実装工程：段階的に、できる限り完成まで進める

### Phase 0 — 候補台帳の監査と選考（必須）

394件を機械的に全採用しないでください。現行辞書との比較を自動化し、次を判定してから実装します。

- ID重複、参照切れ、CSV/JSONの食い違い
- 日本語表記・英文の正規化重複、意味的に同じ候補、別項目への誤分類
- モデルで通用する保証のない抽象タグ、不自然な英文、定型文のまま残った `nat`
- 単一選択フィールドで両立不能な複数要素を含む候補
- 年齢・髪の長さ・世界観・衣装・画角・小物・目隠し・禁断モードと競合する候補
- 既存の機能で十分表現できる候補、新規フィールドが必須の候補

各候補を **採用／修正して採用／統合／保留／不採用** のいずれかに分類し、理由と対応先FieldIdをCSVまたはJSONで記録。394件をどう処理したか全数追跡可能にしてください。安全性や品質を優先し、394件全採用は必須としません。

`en` はタグ出力用、`nat` は自然文出力用として、モデルに適した自然で重複の少ない語句へ推敲。出典URLがあっても個別タグの実機検証済みとは扱わないこと。根拠のない「PixAI/NAI対応保証」は書かない。

### Phase 1 — 既存フィールドへの低リスク増築

添付の Phase 1候補146件を優先し、採用審査を通ったものを既存の `Option` と各辞書に組み込んでください。重点は顔／目元／年齢を感じさせる特徴／体格・骨格／髪型／現代・生活職／衣装／人物の所作／生活背景／成熟美形タイプ。

- `lengths`、`minShot`、`hands`、`worlds`、`culture`、`requires`、`prefs` 等は現行実装で解釈される構造に**翻訳して**設定すること。
- 新しいhard条件は物理的・視覚的に成立しない場合に限定し、softな相性は重みで表すこと。
- 表示名に髪色・年齢・職業が含まれるアーキタイプには、抽選時の整合と画像タグの意味を点検。
- 既存のネガティブ出力、コンパクト出力、フリータグ、LoRA欄と衝突しないこと。

Phase 1完了時点でビルド・既存テスト・新規データテストを通し、実例プロンプトを比較してください。

### Phase 2 — 関連付けと実効的な多様性の向上

Phase 2候補146件を選考・追加。`archetype → 顔・表情・体格`、`職業 → 衣装・小物・背景`、`世界観 → 衣装・背景・光` のsoft相性を改善してください。

**テーマ25件は「素材を組み合わせた設計例」であり、確実に同時選択できるプリセットではありません。** 既存フィールドに2候補を同時採用する例、Phase 3の新フィールドを参照する例、世界観と衣装の不一致があるため、各テーマを「現行で成立／候補修正で成立／新機能後に成立／保留」に分けてください。採用する場合は各テーマが実際に成立し、1人分の自然な出力になることをテストしてください。

- まとまり重視では調和を保ち、バランスでは探索幅を確保し、カオスはhard制約のみ遵守する。
- 単なる候補件数だけでなく、年齢別・容姿別・ポーズ別の到達率、Shannon entropy／実効候補数、複合的な外見署名の類似率を測定する。
- locked 0/5/10/15件程度でstuck率（候補不足で元値保持）と拒否率を測る。調査報告書の約0.21%は旧版の参考値であり、最新mainでベースラインを**実測し直してから**比較する。
- 出力時に白い肌と濃褐色の肌、衣装名と異なる色やパーツ、閉眼とviewer視線などの**意味矛盾**を検出・抑制。過度なhardルール増設は避ける。
- フリータグのsemantic lintは、ユーザーが意図的に設定した表現を勝手に削除せず、警告・修正案中心で扱う。

### Phase 3 — 新フィールド7種類と102候補

候補の有用性と既存システムとの整合を検討し、可能な限り実装。推奨順は：
1. `ageCue` 18件：成熟を示す細かな視覚特徴。35～44／45～59／60+で自然な重み。年齢だけで皺・白髪を強制しない。
2. `gaze` 14件＋`headPose` 12件：身体ポーズと視線・頭の向きを分離。視線だけ／顔の角度だけを固定・再抽選できることを目指す。
3. `hairTexture` 14件＋`fringe` 12件：髪質、前髪、分け目を髪型から独立。長さ・結髪・顔を覆う髪との競合を検証。
4. `outfitDetail` 20件＋`fabric` 12件：衣装の上に適切な細部・素材を付与。親衣装に必要な部位がない場合は無理に適用しない。

**最重要：既存 `pose` に埋め込まれた `looking at viewer` などと `gaze` を二重出力しないこと。** 新フィールド有効時のみ、既存ポーズの視線成分を安全に分離・上書きできる互換層を設計し、無効時の従来出力は守ってください。既存の `angle`（カメラ）と `headPose`（人物）も別物として扱うこと。閉眼・目隠し・片目隠れ・視野外・首や頭の物理的制約・拘束ポーズを検証すること。

7項目を増やしても画面を煩雑にしないよう、**「顔の細部」「髪の細部」「視線・頭部」「衣装の質感」などの折りたたみ式の任意調合**に整理。各行で手動選択／個別再抽選／固定を可能にし、全固定・部分抽選・人物一括固定・保存・共有・戻すに整合させてください。新しい項目を一括固定に含めるかは、その項目が人物の個体識別を定めるかという意味で慎重に決め、意図を説明してください。

**顔の完全分割（faceShape / jawChin / nose / brows / mouth）は今回の394候補では完全設計されていない。** 余裕があっても、仕様不明のまま大規模な分割移行を強行せず、独立した後続改善案にしてください。

### モデル別出力の改善（追加課題）

既存のPixAI／NovelAI／汎用タグ／自然英文／日本語の5形式を消さないまま、可能であれば **PixAI SDXLとTsubaki等DiT、NovelAIのモデル世代に対応する出力サブプロファイル**を検討してください。辞書本体をサービスごとに二重化せず、出力ポリシーを分離する方式を優先します。

- 強調記法、品質タグ、男性1名アンカー、不要な否定タグ、タグ／自然文の比重は各モデル仕様を根拠付きで確認。
- モデルのタグ認識や生成効果は実画像A/B未確認なら断定しない。外部画像生成APIへの接続や有料生成は要求しない。
- 使用者の既存設定を勝手に変更しない。サブプロファイルの追加で旧設定の表示・出力が壊れないようにする。

## 6. 品質保証と受け入れ条件

**最低限必要な検査**：
1. `npm run typecheck`、`npm run lint`、`npm test`、`npm run build`、可能なら `npm run test:browser`。現行コードに合わせて実行し、失敗時は原因を修正する。

3. 3モード×年齢5区分×容姿5区分×主な任意モジュール条件で、数千回以上の抽選を実行。**新規データの到達率、hard違反0、ロック変更0、例外0、年齢下限違反0**を確認。
4. 固定0/5/10/15項目、全ロック、手動採用、個別再抽選、候補除外、候補不足、競合拒否、戻す・進む、seed再現の回帰テスト。

6. 禁断OFF／ON、コスプレOFF／ON、獣人ON／OFF、ひげ・眼鏡・持ち物・背景・髪配色のモジュール境界を全て検証する。禁断やコスプレがOFFの状態で出現する回帰は不可。
7. 320／375／390pxのスマホ表示、タップ範囲、折りたたみ、横スクロールなし、設定欄の可読性、コピー失敗時のフォールバックをブラウザで確認。Safari／実機未検証ならその旨を報告する。

10. 新規条件によりstuck率や候補の実効多様性が悪化した場合は、数字と原因を示して重み・hard/softを調整する。**テストを通すために既存テストを削除したり、失敗を無視したりしない。**

## 9. 最終的な判断基準

**「増築したので394件増えました」では不十分です。** 既存の美青年が守られ、ロックや保存が壊れず、同じ人物像の表情・顔角度・髪質・衣装の変化を利用者が実感できる状態を目指してください。

一方で、後方互換性を損なう危険がある項目は無理に完成扱いしないこと。**候補全件の追跡可能な選考、壊れない実装、検証済みの公開**を優先します。

仕様を読むだけで作業を止めず、GitHubの実態に合わせて自律的に設計・実装・検証まで進めてください。
